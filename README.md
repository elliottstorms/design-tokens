# design-tokens

A small dark-first design system where the accessibility claims are enforced
rather than asserted. Two CSS files, a contrast contract, and a checker that
fails the build when a color stops meeting the level it promised.

Most token repos publish a palette and a sentence about caring how it looks. The
useful part is not the hex values, it is the guarantee that they still measure
what the documentation says they measure after the next redesign.

## The 4.43 problem

This exists because of one number. The brand accent, `--purple` `#b95cff`,
measures **5.18** against the page background and passes AA comfortably. On a
raised card it measures **4.43**, and the floor for normal-size text is 4.5.

That gap is invisible by eye, survives every design review, and shows up the
moment someone runs an audit. The fix is not to abandon the accent, it is to
carry a second variant for the surface where the first one fails:

```css
--purple:        #b95cff;  /* 5.18 on ink. Fine on the page. */
--purple-bright: #c879ff;  /* 5.61 on card. Use inside cards. */
```

and then to make that rule mechanical instead of remembered:

```bash
python3 tools/contrast.py     # exits 1 if any shipped pair drops below its promise
```

## What's here

| Path | What it is |
|---|---|
| `css/tokens.css` | The palette, type, rhythm, and motion tokens. Every color is annotated with its measured ratio on both surfaces. |
| `css/components.css` | The components the tokens were derived from: cards, buttons, status pills, eyebrows, stats, prose. No hardcoded values. |
| `tools/pairs.json` | The contract: every foreground/background pair that actually ships, and the WCAG level it must hold. |
| `tools/contrast.py` | Reads the hex values out of `tokens.css`, measures every pair, exits nonzero on any regression. Stdlib only. |
| `demo.html` | Everything on one page. Open it in a browser, no build step. |

## Use it

```bash
git clone https://github.com/elliottstorms/design-tokens
open design-tokens/demo.html
```

Then copy `css/tokens.css` into your project and import it before anything else.
The components are optional; the tokens are the point.

If you change a color, run the checker. If you add a pair, add it to
`pairs.json` first, so the thing that is supposed to catch you is not something
you can forget to update.

Note that `--purple` on `--card` is listed at AA-large deliberately. It is not a
failure being waved through: it is a documented restriction to headings and
large text, with `--purple-bright` carrying everything smaller. A contract that
records real limits is more useful than one that pretends they do not exist.

## Opinions embedded in the values

**Never pure black or pure white.** `#000` under a light foreground reads as
harsh and flattens depth. `#fff` glares against dark navy. The background is
`#0d162a` and the text is `#f6f0eb`, both deliberately warm.

**One radius, one gap, one shadow, one easing.** Component-specific variants are
how a system decays into forty near-identical numbers nobody can justify later.

**Green is a status and a data color, never a button.** It has exactly one
secondary role (stat numbers and mono labels) and a hard boundary: no CTAs, no
large fills. A full surface of `#4aff9e` is a nightclub, not a status.

**Motion collapses at the token level.** `prefers-reduced-motion` zeroes the lift
and easing tokens once, rather than every component remembering to handle it.

**No light theme.** A dark-tuned palette mechanically inverted produces muddy
accents and failing ratios, and shipping one would make every guarantee above
false. If you need light, measure a new set and give it its own pair list.
